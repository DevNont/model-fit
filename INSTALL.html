ติดตั้งและใช้งาน model-fit

คู่มือสั้นสำหรับ skill ของ Claude Code ที่ช่วยตัดสินใจว่างานไหนทำเอง งานไหนส่งให้ subagent

1. skill นี้คืออะไร

model-fit เป็น skill ที่ช่วยตัดสินใจว่าแต่ละงานควรให้ main thread ทำเอง หรือส่งให้ subagent ทำ และถ้าส่ง ควรใช้ model ไหน

การตัดสินใจนี้ครอบคลุมทุกช่วงของ SDLC คือ วางแผน, เขียนโค้ด, ตรวจสอบ, เขียน docs, และ commit/release

เหตุผลคือ subagent มีต้นทุนคงที่ ได้แก่ context ของตัวเอง, brief ที่ต้องเขียนใหม่, การอ่านไฟล์ซ้ำ, และ report ที่ main thread ยังต้องตรวจอีกรอบ จึงคุ้มก็ต่อเมื่องานใหญ่ ทำขนานกันได้ หรือต้องอ่านไฟล์จำนวนมาก

skill นี้ลดการใช้ token โดยไม่ลดมาตรฐานการตรวจสอบ

2. ประโยชน์ที่ได้

ประโยชน์หลักคือใช้ token น้อยลง โดยงานยังถูกตรวจในมาตรฐานเดิม ยังไม่ได้วัดว่าประหยัดได้เท่าไร

1. ลด token ที่เสียไปกับการเปิด agent โดยไม่จำเป็น

  • subagent มีต้นทุนคงที่ คือ context ของตัวเอง, brief, การอ่านไฟล์ซ้ำ, และ report ที่ยังต้องตรวจ งานแก้ไม่กี่บรรทัดจึงทำบน main thread
  • งานที่แก้เหมือนกันหลายไฟล์หรือหลาย repo ใช้ script loop เดียว ไม่เปิด agent หนึ่งตัวต่อหนึ่งเป้าหมาย

2. ใช้ model ราคาแพงเฉพาะงานที่ต้องใช้

  • haiku สำหรับการค้นหา, sonnet สำหรับงานเขียนที่ระบุชัด, opus สำหรับ implement จริง
  • คนที่มีโควตาน้อยหรือจ่ายตาม token ได้ประโยชน์มากที่สุด

3. session ยาวได้โดย context ไม่เต็มเร็ว

  • งานที่ต้องอ่านไฟล์เยอะส่งให้ agent แล้วได้ report กลับมาไม่เกินราว 25 บรรทัด
  • เมื่อ context ใกล้เต็ม กติกาจะส่งต่อให้ agent มากขึ้น

4. งานเสร็จเร็วขึ้น

  • งานอิสระ (เช่น backend + frontend) ทำขนานกันได้
  • งานต่อเนื่องส่งกลับไปที่ agent ตัวเดิม จึงไม่ต้องอ่านซ้ำ
  • hotfix ข้ามขั้นวางแผนเต็มรูปแบบ

5. คุณภาพไม่ตกเมื่อใช้ model ถูกลง

  • ผลจากทุก agent ถูกตรวจเองก่อนรายงานว่าเสร็จ
  • การตัดสินใจ, commit และ release อยู่บน main thread และไม่ข้ามการตรวจเพื่อประหยัด token

6. ทำงานแบบเดียวกันทุกครั้งและทุกคน

  • ไม่ต้องอธิบายซ้ำว่าเมื่อไรควรใช้ agent หรือใช้ model ไหน
  • ทีมที่ติดตั้ง skill เดียวกันจะแบ่งงานเหมือนกัน และ report จะบอกเสมอว่า model ไหนทำส่วนไหน

ข้อจำกัด

  • เกณฑ์ (2 ไฟล์, ~40 บรรทัด, 3 agent) เป็นค่าเริ่มต้น ไม่ได้มาจากการวัด
  • skill เป็นแนวทางสำหรับ Claude ไม่ใช่การบังคับระดับระบบ Claude จึงอาจไม่ทำตามทุกครั้ง
  • งานเล็กที่ทำบน main thread ใช้ model ของ session นั้น ถ้า session ใช้ model ราคาแพง งานเล็กก็คิดราคานั้น

3. ในไฟล์ zip มีอะไร

  • model-fit/SKILL.md ตัว skill (กติกาแกน)
  • model-fit/references/ อีก 3 ไฟล์ที่ Claude อ่านเฉพาะเมื่อเข้าเคส: expensive-main.md (model หลักราคาแพง), teams-and-workflows.md (ทีม agent / workflow), sdlc.md (ตาราง SDLC / ADLC) ต้อง copy ทั้งโฟลเดอร์
  • model-fit/hooks/ hook บังคับทุก prompt (model-fit-gate.sh) และตัวติดตั้ง (install.js)
  • INSTALL.html คู่มือฉบับนี้

4. วิธีติดตั้ง

เลือกวิธีเดียวที่เหมาะกับคุณ แล้วเปิด session ใหม่ของ Claude Code หลังติดตั้งทุกครั้ง

3a. ส่วนตัว ใช้ได้ทุกโปรเจกต์ (macOS / Linux)

แตก zip แล้วเปิด terminal ในโฟลเดอร์ที่แตกออกมา

mkdir -p ~/.claude/skills && cp -r model-fit ~/.claude/skills/

จากนั้นเปิด Claude Code session ใหม่

3b. ส่วนตัว (Windows, PowerShell)

แตก zip แล้วเปิด PowerShell ในโฟลเดอร์ที่แตกออกมา

New-Item -ItemType Directory -Force "$env:USERPROFILE\.claude\skills"
Copy-Item -Recurse model-fit "$env:USERPROFILE\.claude\skills\"

จากนั้นเปิด Claude Code session ใหม่

3c. ทั้งทีม ผ่าน repo

รันในโฟลเดอร์ root ของ repo

mkdir -p .claude/skills && cp -r model-fit .claude/skills/
git add .claude/skills/model-fit
git commit -m "add model-fit skill"

ทุกคนที่เปิด Claude Code ใน repo นี้จะได้ skill ไปด้วย (หลัง pull แล้วเปิด session ใหม่)

3d. คัดลอกไปเครื่องอื่น

แทน <user> และ <host> ด้วยค่าของเครื่องปลายทาง

scp -r ~/.claude/skills/model-fit <user>@<host>:~/.claude/skills/

จากนั้นเปิด Claude Code session ใหม่บนเครื่องนั้น

5. ตรวจว่าติดตั้งแล้ว

  • พิมพ์ / ใน Claude Code แล้วดูว่ามี model-fit ในรายการ
  • หรือถามว่า มี skill อะไรบ้าง

โครงสร้างโฟลเดอร์สุดท้ายต้องเป็น .../skills/model-fit/SKILL.md

ข้อผิดพลาดที่พบบ่อยคือโฟลเดอร์ซ้อนกัน เป็น skills/model-fit/model-fit/SKILL.md ถ้าเป็นแบบนี้ skill จะไม่ขึ้น ให้ย้ายโฟลเดอร์ข้างในขึ้นมาหนึ่งระดับ

6. วิธีใช้งาน

สามวิธี

  1. เรียกเอง พิมพ์ /model-fit
  2. ให้โหลดเอง skill จะโหลดเมื่อเริ่มฟีเจอร์หรือแก้บั๊ก, เมื่อจะเปิด subagent, เมื่อเลือก model, หรือเมื่อคุยเรื่องประหยัด token
  3. บังคับให้โหลดทุกครั้ง เพิ่มบรรทัดนี้ใน CLAUDE.md 
    ก่อนเริ่มงานฟีเจอร์ แก้บั๊ก refactor หรือเปิด subagent ให้โหลด skill model-fit ก่อนเสมอ

บังคับใช้ทุก session ทุก prompt (hook)

ติดตั้ง skill อย่างเดียว Claude จะโหลดเฉพาะเมื่อเห็นว่างานเข้าข่าย บางงานจึงหลุด ตั้งแต่ 2026-10-21 skill มี hook ในโฟลเดอร์ hooks/ ที่บังคับทุก prompt ของทุกโปรเจกต์บนเครื่อง: โหลด model-fit ก่อน ตัดสินใจผ่าน model-fit และเปิดคำตอบทุกครั้งด้วยบรรทัด model-fit: <split> เช่น model-fit: inline (opus) หรือ model-fit: agent Explore/haiku ×2 + inline verify

ติดตั้ง hook ครั้งเดียวต่อเครื่อง (ต้องมี node ซึ่ง Claude Code ใช้อยู่แล้ว):

node ~/.agents/skills/model-fit/hooks/install.js
ขอบเขตคำสั่งskill ต้องอยู่ที่
ทุกโปรเจกต์บนเครื่องนี้ รวม session ในอนาคตnode ~/.agents/skills/model-fit/hooks/install.js~/.agents/skills/model-fit/ (ติดตั้งด้วย -g)
ทุกคนที่ทำงานใน repo หนึ่งnode .agents/skills/model-fit/hooks/install.js --project ที่ root ของ repo แล้ว commit .claude/settings.json + CLAUDE.md.agents/skills/model-fit/ ใน repo
ถอนเพิ่ม --remove ต่อท้ายคำสั่งเดิม

คำสั่งทำสองอย่าง (รันซ้ำได้ ไม่ซ้อน): ลงทะเบียน hooks/model-fit-gate.sh ที่ SessionStart และ UserPromptSubmit ใน settings.json (สำรองไฟล์เดิมเป็น settings.json.bak-model-fit) และเพิ่มกฎ "always on" ใน CLAUDE.md ระหว่าง <!-- model-fit:begin --> … <!-- model-fit:end --> หลัง npx skills update ให้รันซ้ำ แล้วเปิด session ใหม่ให้ hook เริ่มทำงาน hook เป็นข้อความถึง Claude ทุก prompt ไม่ใช่การบล็อกระดับระบบ แต่มาพร้อมกฎใน CLAUDE.md และ §0 ของ skill จึงหลุดยากกว่าบรรทัดเดียวใน CLAUDE.md มาก

7. กติกาโดยย่อ

ทำเองหรือส่งต่อ

ทำเอง (inline) เมื่อครบทุกข้อส่งต่อให้ subagent เมื่อมีข้อใดข้อหนึ่ง
ไฟล์ถูกอ่านใน conversation นี้แล้ว หรือรู้เป้าหมายแน่ชัด
ไม่เกิน ~2 ไฟล์ และแก้ไม่เกิน ~40 บรรทัด
ไม่เหลือการตัดสินใจด้านออกแบบที่ยังเปิดอยู่
นอกจากนี้ งานที่แก้เหมือนกันแบบกลไกหลายไฟล์หรือหลาย repo ให้ทำเองด้วย script loop แล้วตรวจด้วย grep 		ตั้งแต่ 3 ไฟล์ขึ้นไป หรือฟีเจอร์ที่มี test และ docs ของตัวเอง
มีงานอิสระตั้งแต่สองชิ้นที่ทำขนานกันได้ (เช่น backend + frontend)
ต้องอ่านไฟล์จำนวนมากที่ยังไม่เคยอ่าน (สำรวจ, audit, ขุด log)
แก้ซ้ำหลายเป้าหมายที่ต้องใช้ดุลยพินิจรายเป้าหมาย
อยู่ใน layer ที่มีกติกาเข้มเกินกว่าไม่กี่บรรทัด

ไม่ส่งต่อ: การค้นหาที่รู้เป้าหมายแล้ว, การเช็คที่ใช้คำสั่งเดียว, diff ที่เล็กพอจะอ่านเอง ถ้า session ยาวหรือ context ใกล้เต็ม ให้ลดเกณฑ์ inline ลง

เลือก model ตามงาน

Modelใช้กับ
haikuงานอ่านอย่างเดียวที่ตรวจคำตอบได้ เช่น หาตำแหน่ง, ไล่ดูการใช้งาน, สรุป log
sonnetงานเขียนที่ขอบเขตชัดและระบุครบ เช่น แก้ตามบรรทัดที่ระบุ, CSS, copy, changelog, docs, test ตามแบบที่มีอยู่
opusงาน implement จริง เช่น ฟีเจอร์หลายไฟล์, backend, state / concurrency / migration / auth, งานที่ยังมีทางเลือกด้านออกแบบ
fableเฉพาะ second opinion ด้านออกแบบ, ไล่หา root cause ที่ติดอยู่, review เชิงตรงข้ามกับงานเสี่ยง ไม่ใช้สร้างงาน

ลังเลระหว่างสองระดับ: ขึ้นหนึ่งระดับสำหรับสิ่งที่ถึงผู้ใช้ ลงหนึ่งระดับสำหรับงานอ่านอย่างเดียว เลือกต่องาน ไม่ใช่ต่อ session

ใครรับผิดชอบแต่ละช่วง SDLC

ช่วงผู้ทำModelกติกา token
1 เข้าใจและวางแผนmain thread; ใช้ search agent เฉพาะเมื่อยังไม่รู้ pattern ที่จะอิงhaiku สำหรับการค้นหาหา pattern เดิมมาอิงหนึ่งตัวแล้วหยุดค้น
2 Implementinline หรือ builder ขนานกันตามหัวข้อ "ทำเองหรือส่งต่อ"opus / sonnet ตามตาราง modelbrief ระบุไฟล์ pattern ที่ต้องอิง
3 ตรวจสอบmain thread-ตรวจเองจริง ไม่ข้ามเพื่อประหยัด token
4 Docsinline ถ้าเป็นหนึ่งบรรทัดหรือหนึ่งย่อหน้า ไม่เช่นนั้นใช้ agent เดียวทั้งชุดsonnetไม่ใช้หนึ่ง agent ต่อหนึ่งไฟล์
5 Commit · push · releasemain thread ไม่ส่งต่อ-สถานะ git และ deploy ต้องเห็นเอง

ขนาดของรอบงาน

  • Hotfix / แก้บรรทัดเดียว: ทำช่วง 2, 3, 5 แบบ inline ไม่ใช้ agent ไม่ต้องมี plan file
  • ฟีเจอร์เล็ก (repo เดียว ไม่กี่ไฟล์): แผนสั้นไม่กี่บรรทัด ทำ inline หรือใช้ sonnet หนึ่ง agent แล้ว verify และ commit
  • ฟีเจอร์ข้าม layer: วางแผนก่อน ใช้ opus builder ขนานกัน ใช้ sonnet หนึ่งรอบสำหรับ docs, main thread ตรวจเอง และประกาศถึงผู้ใช้ถ้าโปรเจกต์มีช่องทางนั้น

ทีม agent และ workflow

เมื่องานต้องใช้ agent มากกว่าหนึ่งตัว มีสามชั้นเรียงตามต้นทุน ขึ้นชั้นถัดไปเฉพาะเมื่อชั้นที่ถูกกว่าทำไม่ได้

ชั้นคืออะไรใช้เมื่อ
agent ขนานกันเรียก Agent 2-3 ตัวในข้อความเดียว แต่ละตัวอิสระ รายงานกลับ main threadงานอิสระที่ไม่ต้องเรียงลำดับกัน
ทีม agentagent ไม่กี่ตัวที่มี role ต่างกัน (builder · reviewer · docs) main thread เก็บไว้ตลอดงานและคุยต่อผ่าน SendMessageงานวนหลายรอบ (สร้าง → ตรวจ → แก้) และแต่ละรอบต้องใช้ context เดิมของ role นั้น
workflowscript ที่สั่ง agent เป็นลำดับแน่นอน (pipeline / parallel / phase) รันเบื้องหลังมีขั้นที่ขึ้นต่อกันตั้งแต่ 4 ขั้น หรือกระจายงานไปหลาย target และผู้ใช้สั่งเองเท่านั้น
  • workflow เปิดโดยผู้ใช้เท่านั้น: ใช้ agent เป็นสิบตัวในรอบเดียวได้ Claude จะเปิดเมื่อผู้ใช้สั่ง (เช่นคำว่า ultracode, "use a workflow" หรือ skill ที่กำหนดไว้) ถ้าไม่ได้สั่ง ให้บอกว่าจะทำอะไรและต้นทุนราวเท่าไร แล้วถามก่อน งานที่ "น่าจะได้ประโยชน์" ไม่นับ
  • ขนาดทีมตามจำนวนรอบ ไม่ใช่จำนวนไฟล์: ทุกรอบจ่าย context ของทุกคนในทีม สอง role (builder + reviewer) พอสำหรับงานส่วนใหญ่ เพิ่ม role ที่สามเมื่อ docs หรือ test เป็นสายงานแยก เกินสาม workflow ถูกกว่าและคาดเดาได้กว่า
  • builder กับ reviewer เป็น agent คนละตัว และคนละ model ถ้าทำได้: reviewer ที่เห็น context หรือข้อสรุปของ builder จะเอนตาม ให้ส่ง diff กับ spec ไม่ส่ง report ของ builder ตรวจ style/gate ใช้ model ต่ำกว่าหนึ่งขั้น ตรวจ design/ความเสี่ยงใช้สูงกว่าหนึ่งขั้นหรือ main thread
  • main thread เดียวเป็นเจ้าของทีม: สมาชิกรายงาน main thread ไม่รายงานกันเอง การส่งข้อความระหว่างสมาชิกใช้ส่งของที่จับต้องได้ (path, ชื่อ test ที่พัง) ไม่ใช่ตัดสินใจ
  • หาของเดิมก่อนเปิดใหม่: ดู ListAgents ว่ามี agent หรือ session ที่ถือ context เรื่องนั้นอยู่แล้วไหม (ผู้ช่วยเดิม, session อื่นบน repo เดียวกัน, cloud session) ส่งข้อความหาเสียหนึ่งรอบ เปิดใหม่เสียการอ่านทั้งหมด และไม่ส่งงานไป session ที่ผู้ใช้ไม่ได้บอกว่าใช้ได้
  • ตั้งงบทั้งงาน ไม่ใช่แค่จำนวนพร้อมกัน: "3 ตัวพร้อมกัน" เป็นเกณฑ์ต่อข้อความ ทีมหรือ workflow ให้ตั้งงบจำนวน agent ทั้งงานไว้ก่อน (workflow ขนาดกลางไม่เกิน 10 agent) ถึงงบแล้วหยุดรายงาน ไม่เปิดเพิ่มเงียบ ๆ
  • งานเบื้องหลังไม่ต้อง poll: ทีมและ workflow แจ้งเองเมื่อเสร็จ ไม่เปิดหรือปลุก agent เพื่อไปดูอีกตัว รอการแจ้ง และไม่ทายผลล่วงหน้า
  • การตรวจไม่ลดลงตามขนาดทีม: ผลงานของทุกสมาชิกและผลสุดท้ายของ workflow ต้องผ่านการตรวจเองของ main thread คำตัดสินของ reviewer agent เป็นข้อมูลประกอบ ไม่ใช่ตัวแทน

กติกาที่เพิ่ม 2026-10-18

  • เลือกชนิด agent ก่อนเลือก model: งานค้น/ตรวจใช้ agent แบบอ่านอย่างเดียว (Explore หรือ investigator ของโปรเจกต์) จะได้แก้ไฟล์ไม่ได้โดยบังเอิญ งานสร้างใช้ builder ของโปรเจกต์ถ้ามี แล้วค่อยเลือกระดับ model ในชนิดนั้น
  • fork ใช้เมื่อไหร่: ใช้ model เดียวกับแม่และสืบทอด context ทั้งหมด จึงเหมาะเฉพาะเมื่อ brief จะต้องเล่า session นี้ซ้ำยาว ๆ (เช่น review สิ่งที่ตัดสินไปในรอบนี้) และห้ามใช้ปลาย session ยาว เพราะจ่าย context ทั้งก้อนอีกครั้ง
  • ไม่ตั้ง effort เอง: ปล่อยค่าเริ่มต้นของ agent เว้นแต่ผู้ใช้หรือกฎโปรเจกต์สั่ง ตัวเลือก model คือคันโยกของ skill นี้
  • brief มี template: Goal / Ruled out / Read / Touch / Mirror / Rules / Gates / Report ≤ 25 บรรทัด กรอกทุกบรรทัด ไม่ลบบรรทัดไหน model เล็กทำตามโครงได้ดีกว่าอ่านคำบรรยาย
  • builder ขนานบน repo เดียว ใช้ isolation: worktree: แต่ละตัวได้ worktree ของตัวเอง ไม่เขียนทับกัน worktree ที่ไม่มีการเปลี่ยนแปลงถูกเก็บกวาดเอง agent อ่านอย่างเดียวไม่ต้องใช้
  • แก้ซ้ำได้ 1 รอบ แล้วยกระดับ: ผลงานผิดหรือไม่ครบ ส่งคำแก้ 1 ครั้งให้ agent ตัวเดิมโดยระบุช่องว่างให้ชัด ถ้ารอบสองยังผิด หยุด ทำเองหรือเริ่มใหม่ด้วย model สูงกว่าหนึ่งขั้น ไม่มีรอบที่สามกับตัวเดิม
  • สัญญาณว่า context เต็ม: มี compaction summary แทนบทสนทนาเก่าแล้ว · กำลังจะอ่านไฟล์ที่เคยอ่านซ้ำ · ต้องเลื่อนกลับไปดู output เก่าเพื่อตอบ · งานข้ามวันบน session เดิม เจอข้อใดข้อหนึ่ง ให้ลดเกณฑ์ inline ลงทันที
  • รายงานปิดงานบอกว่า model ไหนทำอะไร: บล็อก "Who did what" หนึ่งบรรทัดต่อชิ้น รวมชิ้นที่ทำเองบน model หลัก ชิ้นที่ส่งต่อระบุชนิด agent/model, จำนวนรอบ และ main thread ตรวจด้วยอะไร ใส่ model ที่ทำจริง (ถ้าถูกปฏิเสธแล้วลดระดับ ให้บอกระดับที่ทำ) ชิ้นที่ไม่ได้ตรวจอยู่ใต้ "Not verified" เสมอ
  • บันทึกทุกงานที่ส่งต่อ 1 บรรทัด: delegated: <job> · <agent type>/<model> · <n> rounds · redo: yes/no · <why> ลง work log หรือ prompt log ของโปรเจกต์ เป็นข้อมูลชุดเดียวที่ใช้ปรับตัวเลขเกณฑ์ในหัวข้อ "ปรับค่า"

ADLC: gate ต่อช่วงและวงจร calibrate

ตาราง SDLC ใน references/sdlc.md ทำแบบ agentic development lifecycle: agent ทำงานข้างในช่วง คนเป็นผู้ผ่าน gate ที่ปิดช่วงนั้น และวงจรไม่จบที่ release

ช่วงgate ที่ปิดช่วง (คนผ่าน)agent ในช่วงนี้ทำได้แค่
1 เข้าใจและวางแผนแผนที่ main thread เขียนและผู้ใช้รับ (งานเล็ก: ไม่กี่บรรทัดที่บอกก่อนลงมือ)อ่านอย่างเดียว ไม่แก้ ไม่ git
2 ลงมือทำmain thread อ่าน git diff --stat และ hunk ที่เสี่ยงแล้วแก้เฉพาะ path ใน brief, รัน gate, ไม่ commit/push/deploy
3 ตรวจgate เขียว + ตรวจพฤติกรรมจริงหนึ่งครั้งด้วยตัวเอง สิ่งที่ไม่ได้ตรวจต้องบอกreviewer อ่าน diff แล้วรายงาน ไม่แก้อะไร
4 เอกสารmain thread อ่าน diff ของเอกสารแล้วแก้เฉพาะไฟล์เอกสารที่ระบุ
5 commit · push · releaseผู้ใช้อนุมัติตามที่โปรเจกต์กำหนด เห็นสถานะ git/deploy ด้วยตัวเองไม่มี agent ในช่วงนี้
6 calibrateเขียนบรรทัด delegated: ของงานแล้ว ทบทวนตัวเลขเกณฑ์ตอน retro หรือเมื่อ redo: yes ซ้ำสองครั้ง—

agent ไม่ผ่าน gate ของตัวเอง ช่วงที่ gate ยังไม่ผ่านไม่เริ่มช่วงถัดไป สิทธิ์แคบที่สุดเป็นค่าเริ่มต้น และไม่มี agent ช่วงไหน commit, push หรือ deploy

เมื่อ model หลักราคาแพง

ใช้เมื่อ session หลักเป็น model ระดับบนสุด (fable หรือ opus ตอนโควตาตึง) ต้นทุนของงานเล็กไม่ได้อยู่ที่จำนวนบรรทัด แต่อยู่ที่ทุกรอบของ main thread ต้องอ่าน context ทั้งหมดซ้ำ skill จึงให้ทำ 5 อย่างนี้

กติกาทำอย่างไร
ลดจำนวนรอบบน main threadแก้หลายจุดในรอบเดียว ใช้ script กับงานแก้ซ้ำ ไม่อ่านไฟล์ที่เพิ่งเขียนซ้ำ
ทำเองเฉพาะงานจิ๋วไฟล์เดียว ราว 10 บรรทัด และอ่านไฟล์ไว้แล้ว
ผู้ช่วยประจำ sessionเปิด subagent sonnet หนึ่งตัวตอนมีงานเล็กชิ้นแรก แล้วส่งงานเล็กทุกชิ้นให้ตัวเดิม เปิดตัวใหม่เมื่อย้ายไปส่วนอื่นของโค้ดที่ไม่เกี่ยวกัน ผู้ช่วยไม่ตัดสินใจด้านออกแบบ และไม่ commit
รวมงานเล็กเป็นชุดส่งเป็นรายการเดียว ขอรายงานเดียว ไม่กักงานที่ผู้ใช้รออยู่ และส่งให้หมดก่อนตรวจ
บอกผู้ใช้เมื่อเข้าช่วงงานซ้ำ ๆแจ้งหนึ่งครั้งว่าช่วงนี้ใช้ model ถูกกว่าได้ (/model sonnet) และควรสลับกลับเมื่อถึงขั้นวางแผนหรือตรวจ ผู้ใช้เป็นคนสลับเอง

ถ้า session หลักเป็น model ระดับกลางอยู่แล้ว ข้ามหัวข้อนี้ และใช้เกณฑ์ 2 ไฟล์ / ราว 40 บรรทัดตามตารางด้านบน

8. ถ้าไม่ได้ใช้ครบทุก model

แต่ละ plan และการตั้งค่า API ใช้ได้ไม่ครบเหมือนกัน พิมพ์ /model เพื่อดูว่า session ของคุณใช้ model อะไรได้บ้าง แล้วลดระดับตามตารางนี้แทนที่จะให้งานล้ม

กรณีให้ทำอย่างไร
ไม่มี fableใช้ model ที่แรงที่สุดที่มีสำหรับงาน second opinion หรือข้าม second opinion แล้ว review ให้ละเอียดขึ้นบน main thread
ไม่มี opus หรือมีน้อยให้ sonnet สร้างงาน โดยเขียน brief ให้ชัดขึ้น (ระบุไฟล์ pattern, ฟังก์ชันที่แน่ชัด, edge case) และลดขอบเขตต่อ agent ส่วนการตัดสินใจด้านออกแบบอยู่บน main thread
มี model เดียวคอลัมน์ model ไม่มีผลแล้ว แต่กติกาที่เหลือยังใช้ได้ การส่งต่อประหยัด context ไม่ใช่ต้นทุน model จึงส่งต่อเฉพาะงานขนานและงานอ่านที่ท่วม main context
limit ตึงหรือจ่ายตาม tokenยกเกณฑ์ inline ขึ้น (ใช้ agent น้อยลง), จำกัดงานพร้อมกันที่ 1-2, ใช้ haiku กับทุกการค้นหา และไม่กระจายการตรวจเดียวกันให้หลาย agent

ถ้าการระบุ model ถูกปฏิเสธ อย่าลองซ้ำ ให้ลงไประดับถัดไปและบอกว่า model ไหนทำงานจริง

9. กติกาของโปรเจกต์มาก่อน

ถ้า CLAUDE.md หรือ memory ของโปรเจกต์มีกติกาของตัวเองเรื่องชนิด agent, gate, หรือขั้นตอน release ให้ใช้กติกาของโปรเจกต์ก่อน skill นี้ให้แค่เกณฑ์การแบ่งงานและวินัยเรื่องต้นทุน

10. อัปเดตและถอนการติดตั้ง

  • อัปเดต: แทนที่โฟลเดอร์ model-fit ด้วยฉบับใหม่ แล้วเปิด session ใหม่
  • ถอนการติดตั้ง: ลบโฟลเดอร์ model-fit ออกจาก skills/ แล้วเปิด session ใหม่

11. ปรับค่า

ตัวเลขใน skill (2 ไฟล์, ~40 บรรทัด, report ~25 บรรทัด, 3 agent) เป็นค่าเริ่มต้น ไม่ได้มาจากการวัด

ถ้า subagent ส่งงานกลับมาแล้วต้องแก้ใหม่บ่อย ให้เข้มขึ้น ถ้า main context เต็มบ่อย ให้ผ่อนลง
